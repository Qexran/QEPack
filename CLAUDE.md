## Project Overview

QEPack is a cross-platform embedded hardware abstraction library supporting **STM32** (ST) and **TI MSPM0G3507** (Cortex-M0+) microcontrollers. It provides object-oriented, modular peripheral drivers — similar in spirit to STM32CubeMX but with a unified API across platforms.

Target hardware: `LP_MSPM0G3507` LaunchPad. The current active platform is **STM32** (see `QEPack/qepack_settings.h`).

## Build System

This is a **TI Code Composer Studio (CCS) Theia** project (v70.4.0). There is no standalone Makefile or CLI build.

- **IDE**: CCS Theia with SysConfig 1.25.0 and MSPM0 SDK 2.9.0.01
- **Compiler**: TI Arm Clang (`TICLANG_4.0.4.LTS`), targeting `cortex-m0plus` / `thumbv6m`, soft-float ABI
- **SysConfig file**: `empty.syscfg` — configures pins, peripherals, and generates `ti_msp_dl_config.h` into the `Debug/` output directory
- **Build output**: `Debug/<ProjectName>.out` (ELF)
- **Compilation database**: `Debug/.clangd` (auto-generated by CCS, used by clangd for IDE support)

Building and debugging is done inside CCS Theia. The `.ccsproject` and `.cproject` files contain all build settings.

## Architecture

### Platform Abstraction

Two platforms are supported via compile-time `#define QEPACK_PLATFORM` in `qepack_settings.h`:
- `TI` — TI MSPM0, using DriverLib (`ti_msp_dl_config.h`)
- `ST` — STM32, using STM32 HAL (`stm32f4xx_hal.h`)

`QEPack/ti_platform.h` provides a HAL-like abstraction for the TI platform (GPIO, I2C, UART, Timer, ADC), mirroring STM32 HAL naming conventions so device code can be platform-agnostic. Per-platform helpers in `QEPack.h` (`TI_GET_I2C_STRUCTURE`, `TI_GET_TIMER_STRUCTURE`, etc.) convert SysConfig-generated symbols into the in-house parameter structs.

### 1ms Tick Execution Flow (系统心跳)

The entire time-driven subsystem runs on a 1ms hardware timer tick. The call chain is:

Hardware Timer ISR → `vTimerTickHandler()` → `vDevicePeriodExecute()`

`vDevicePeriodExecute()` (in `QEPack/it_controller.c`) is the central dispatcher — it calls every enabled module's `vXxxDevicePeriodExecute()` in sequence. Modules that need periodic updates (LED breath/blink, servo smoothing, key debounce, step machine, motor control, encoder speed calc) hook into this single call chain. There is no RTOS — everything runs in the timer ISR context or the main loop.

### Module System

Every hardware peripheral is an independent "device" module. Each module is enclosed in its own `#if <MODULE>_IS_ENABLE` compile guard. Module selection and device counts are configured in **`QEPack/project_config.h`** (the central configuration file).

In `project_config.h`, each module follows this convention:
- `<MODULE>_IS_ENABLE` — compile-time switch (0/1)
- `<MODULE>_DEV_NUM` — how many instances
- `<MODULE>_DEFAULT_*` — per-module default parameters (e.g., servo PWM freq, PID limits)
- Shorthand aliases: `#define LED0 emLedDevNum0` — maps user-friendly names to enum values

To add a module to a project:
1. Enable it in `project_config.h` (set `<MODULE>_IS_ENABLE` to `1`)
2. Include `QEPack.h` — it conditionally pulls in all enabled modules
3. Initialize the device with its `vXxxDeviceInit()` in user code

Implemented modules: UART (DMA + ring buffer + frame detection), LED (static/blink/breath), Key (click/double/long/press), OLED (SW/HW I2C, printf-style), Servo (180°/360°, smooth), ADC (multi-channel + DMA), Encoder (TIM/GPIO modes), PID (positional/incremental, anti-windup), Motor base class (VTable), DC Gear Motor, EMM Step Motor, Ultrasonic, Linear CCD, Gray Sensor, W25Q64 Flash, Kalman Filter, MPU6050, BNO08X, IMU660RB, HWT101, ATK-MS901M, QMC5883 Compass, HC05 Bluetooth, Timer Controller, Step Machine, Counter Controller, Joystick, Sensor (VTable base class for sensor fusion).

### Object-Oriented Design Patterns

**Standard device pattern** (LED, Servo, Key, UART, etc.):
- `stXxxStaticParamTdf` — hardware pin/peripheral assignment (set once at init)
- `stXxxRunningParamTdf` — runtime state and mode configuration
- `stXxxDeviceParamTdf` — wraps both above
- `vXxxDeviceInit()` — initialize static (hardware) parameters
- `vXxxDeviceRunningParamInit()` — initialize runtime parameters
- `vXxxDevicePeriodExecute()` — called every 1ms via `vDevicePeriodExecute()` for time-based features (blink, breath, smooth servo)

**Motor VTable pattern** (`motor_device.h`):
- `stMotorVTableTdf` — virtual method table with function pointers (`vInit`, `vPeriodExecute`, `vStop`, `vEnable`, `vPosControl`, `vVelControl`)
- `stMotorDeviceTdf` — base "class" struct containing type, VTable pointer, and state
- Subclasses (gear motor, EMM stepper) embed `stMotorDeviceTdf` as their **first member** and implement the VTable functions
- Motors are registered into a global array `g_astMotorDevices[]` and called polymorphically via `vMotorPosControl()`, `vMotorVelControl()`, etc.
- Multi-motor synchronization: commands with `bSyncFlag=1` are queued; `vMotorSynchronousMotion()` fires them all at once.

**Sensor VTable pattern** (`sensor_device.h`):
- Same VTable architecture as Motor, but for sensors
- `stSensorVTableTdf` — virtual methods: `vInit`, `vPeriodExecute`, `fGetValue`, `fGetAccumulatedValue`, `vReset`, `vSetTarget`, `fGetTarget`
- `stSensorDeviceTdf` — base struct with built-in complementary filter weight, optional PID controller binding, and PID output tracking
- Subclasses: MPU6050, ATK-MS901M, IMU660RB, BNO08X, HWT101, Gray Sensor, Linear CCD — each registers via `vXxxSensorRegister()`
- Unified API: `fSensorGetValue()`, `vSensorSetTarget()`, `fSensorFuseValue()` (complementary filter fusion of two sensors)

### Step Machine (`step_machine.h`)

A lightweight state machine using C variadic arguments for initialization. Steps have callbacks, timeout detection, and rule-based transitions. Called periodically from the timer ISR (`vStepPeriodExecute`) and the main loop (`vStepProcess`).

### Timer Controller (`timer_controller.h`)

A software timer system built on a 1ms hardware tick. Register callbacks to fire at arbitrary intervals.

### Interrupt Handling

`QEPack/ti_interrupt.h` defines macro templates that generate ISR functions. Each macro takes a peripheral instance name and optional device number, then expands to a complete interrupt handler. Available macros:

- `CREATE_1MS_TIMER_HANDLER(TIMER_NAME)` — generates the 1ms system tick ISR (calls `vTimerTickHandler()` + `vDevicePeriodExecute()`)
- `CREATE_UART_IRQ_HANDLER(UART_NAME, emDevNum)` — generates UART RX ISR with error recovery (reads FIFO on error to prevent IRQ storms)
- `CREATE_ENCODER_HANDLE_TIMER_HANDLER(TIMER_NAME, emDevNum)` — encoder speed calculation timer
- `CREATE_ENCODER_COMPARE_TIMER_HANDLER(TIMER_NAME, emDevNum)` — encoder capture/compare ISR
- `CREATE_ADC12_0_IRQ_HANDLER(ADC_NAME, emDevNum)` — ADC conversion complete ISR

`QEPack/ti_interrupt.c` instantiates these macros for the TI platform. `QEPack/st_interrupt.c` is the STM32 equivalent (uses standard HAL callback overrides instead of macros). When adding a new peripheral that uses interrupts, the ISR wiring goes here.

## Key Configuration Files

| File | Purpose |
|---|---|
| `QEPack/qepack_settings.h` | Select target platform (`TI` or `ST`), debug mode toggle |
| `QEPack/project_config.h` | Enable/disable modules, set device counts, configure per-module defaults, device alias macros |
| `QEPack/QEPack.h` | Umbrella header — conditionally includes enabled modules + platform struct helper macros |
| `QEPack/it_controller.c` | Central 1ms dispatcher — calls every enabled module's `vXxxDevicePeriodExecute()` |
| `QEPack/ti_interrupt.c` | TI platform ISR instantiation (macro-based) |
| `QEPack/st_interrupt.c` | STM32 platform ISR instantiation |
| `empty.syscfg` | TI SysConfig — pin mux, peripheral assignment (generates `ti_msp_dl_config.h`) |
| `Core/Src/main.c` | Application entry point |

## Code Conventions

- **Naming**: Hungarian-like prefixes — `v` (void func), `em` (enum), `st` (struct), `pst` (pointer to struct), `u32`/`u16`/`u8` (unsigned int widths), `f` (float), `pc` (char pointer), `puc` (unsigned char pointer), `ul` (unsigned long), `b` (boolean/flag)
- All public functions and types use the module name as prefix (e.g., `vLedOn()`, `stServoStaticParamTdf`)
- `.c`/`.h` files use `_device` suffix for peripheral drivers, `_controller` for logic modules
- Device count enums use `emXxxDevNumTdf` pattern with `emXxxDevNum0`, `emXxxDevNum1`, etc.
- Status return type is `QE_StatusTypeDef` (`QE_OK`, `QE_ERROR`, `QE_BUSY`, `QE_TIMEOUT`, `QE_IDLE`)
- `project_config.h` alias convention: `#define LED0 emLedDevNum0` creates a user-friendly name that maps to the enum — device code references `LED0`, not `emLedDevNum0`


Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.
